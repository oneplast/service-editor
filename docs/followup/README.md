# Followup 운영 메모

이 디렉토리는 세션이 끊기거나 컨텍스트가 길어졌을 때, 진행 중 작업을 짧은 문서 하나로 다시 복구하기 위한 경로다.

이 경로는 공식 제품 정책이나 장기 작업 로그를 두는 곳이 아니다. 목적은 기억이 아니라 복구다.

## 무엇을 여기에 두는가

- 여러 턴에 걸쳐 이어지는 작업의 현재 상태
- 긴 문서/코드 탐색 중 다시 읽어야 할 최소 기준
- 세션 재시작 시 바로 열어야 하는 다음 액션
- 현재 작업 범위 검증에 사용할 scope 파일 경로
- 코드/계약 변경 작업의 현재 검증 단계

## 무엇을 여기에 두지 않는가

- 공식 요구사항, 채택된 정책, ADR
- 장기 보관용 작업 로그
- 개인 학습 메모
- 이미 끝난 작업의 상세 검증 기록

## 기본 운영 규칙

- 작업마다 파일 하나만 사용한다.
- 파일은 누적 로그가 아니라 현재 상태 스냅샷으로 유지한다.
- 새 사실이 생기면 계속 덧붙이지 말고, 완료된 내용은 줄이고 최신 상태만 남긴다.
- 관련 없는 여러 작업을 한 파일에 섞지 않는다.
- 다음 세션에서 이 파일 하나만 읽어도 바로 재개할 수 있어야 한다.
- 반복 절차가 필요하면 [`.codex/skills/followup-handoff/SKILL.md`](https://github.com/oneplast/service-editor/blob/dev/.codex/skills/followup-handoff/SKILL.md)를 따른다.
- 문서 영향 판정과 공식 문서 갱신 대상은 [`.codex/config/doc-update-matrix.md`](https://github.com/oneplast/service-editor/blob/dev/.codex/config/doc-update-matrix.md)를 따른다.
- `.codex/scripts/check-doc-governance.sh`는 문서 체계·규칙·workflow 계약을 바꾼 작업에서만 사용한다.
- 작업 범위 검증이 필요하면 `.codex/scripts/*.sh --scope-file <path>` 형태로 현재 작업 파일 목록을 넘긴다.
- scope 파일 경로가 표준 형태가 아니거나 followup 파일을 명시해야 하면 `.codex/scripts/*.sh --followup-file <path>`를 함께 넘긴다.
- 코드/계약 변경 작업은 `현재 상태`에 `검증 단계: 진행 중` 또는 `검증 단계: 검증 대기`를 적는다.
- `진행 중`은 구현을 이어가는 단계다. 이때는 필요할 때만 컴파일, 아주 좁은 테스트, sanity check를 선택하고 전체 PASS 게이트는 유예한다.
- `검증 대기`는 기능 단위를 닫을 준비가 된 단계다. 최초 검증을 실행해 PASS를 닫고, 실제 `FAIL`이 발생한 경우에만 해당 결과 파일을 `verify-and-retry`에 전달한다.

## 언제 생성하거나 갱신하는가

1. 여러 단계에 걸친 작업을 시작할 때
2. 여러 턴을 넘기거나 컨텍스트 압축이 예상될 때
3. 리베이스, 충돌, 복합 검증처럼 목표·제약·scope·검증 상태를 복구해야 할 때
4. 진행 중인 긴 작업에서 구현/문서 반영/검증 단계가 바뀔 때
5. 복구가 필요한 작업이 끝나지 않은 채 턴을 마칠 때

단순 질문, 한 번에 끝나는 수정, 기준 문서 수만 늘어난 작업, 현재 상태 복구가 필요 없는 검증에는 생성하지 않는다.

## 읽기 기준

- followup은 항상 하나만 읽는다.
- 사용자가 특정 파일을 지목했으면 그 파일만 읽는다.
- 특정 파일 지시가 없으면 `docs/followup/active/`에서 현재 작업 파일 하나만 읽고 시작한다.
- followup을 읽은 뒤에는 그 파일이 가리키는 공식 기준 문서만 추가로 읽는다.
- 세션 재개 후 실패·반복 실수·복구 신호가 남아 있을 때만 관련 runbook 파일 하나로 추가 분기한다.

## 파일 위치와 이름

- 진행 중 작업 파일은 `docs/followup/active/` 아래에 둔다.
- 파일명은 `kebab-case` 작업명으로 정한다.
  - 예: `editor-save-api.md`
  - 예: `docs-governance-harness.md`
- 완료된 작업은 파일을 삭제하거나, 정말 장기 보관 가치가 있으면 `prompts/worklog/` 또는 적절한 공식 문서로 옮긴다.
- scope 파일은 가능한 한 `docs/followup/active/<slug>.scope`처럼 같은 작업명으로 둔다.
- 게이트 결과와 PASS fingerprint는 `docs/followup/active/.state/<slug>-<gate>.state`에 두고 followup에는 필요한 경로만 남긴다.
- `docs/followup/active/`에는 동시에 여러 작업 파일을 쌓지 않는다. 진행 중 작업 기준으로 하나만 유지하는 것을 기본 원칙으로 한다.

## 필수 구조

모든 followup 파일은 아래 섹션만 유지한다.

1. `목표`
2. `고정 제약`
3. `읽은 기준 문서`
4. `현재 파일 범위`
5. `현재 상태`
6. `다음 작업`

각 섹션은 짧게 쓴다.

- `목표`
  - 이번 작업이 끝나면 무엇이 달라져야 하는지
- `고정 제약`
  - 다시 흔들면 안 되는 결정, 사용자가 명시한 조건
- `읽은 기준 문서`
  - 다시 읽어야 하는 공식 문서 경로만
- `현재 파일 범위`
  - 이미 본 파일과 앞으로 볼 핵심 파일만
  - 검증 범위를 고정해야 하면 `.scope` 파일 경로를 같이 적는다.
- `현재 상태`
  - 완료된 핵심 단계와 미완료 상태
  - 코드/계약 변경이 있으면 `검증 단계: 진행 중` 또는 `검증 단계: 검증 대기`
- `다음 작업`
  - 재시작 직후 바로 할 1~3개 액션

## 길이 제한

- 가능하면 120줄 이하, 400단어 안팎을 유지한다.
- 길어지면 기록을 늘리는 대신 내용을 다시 압축한다.
- 상세 근거와 장문 비교는 공식 문서나 worklog로 옮기고, followup에는 링크만 남긴다.

## 템플릿과 정리

- 새 파일은 [docs/followup/000-active-task-template.md](https://github.com/oneplast/service-editor/blob/dev/docs/followup/000-active-task-template.md) 기준으로 만든다.
- 템플릿의 빈 항목은 `-`와 `1.`처럼 placeholder만 두고, 불필요한 trailing whitespace를 남기지 않는다.
- 작업이 끝났고 다시 이어갈 필요가 없으면 파일을 삭제한다.
- 후속 작업이 남아 있으면 완료 항목은 지우고 다음 세션에 필요한 최소 상태만 남긴다.
